# Coding Agent 的双层循环

下面的流程图保留了这篇笔记的核心：外层循环（Outer Loop）接收新的用户任务，内层循环（Inner Loop）推进当前任务。理解这个划分，可以把模型生成、工具执行和对话历史三个职责连起来。

```text
coding agent的核心：
外层循环：等待用户输入一个任务
    ↓
内层循环：请求模型 → 执行工具 → 把结果交回模型
    ↑                         ↓
    └──── 模型还要用工具 ──────┘
                              ↓
                         模型直接回答
                              ↓
                        回到外层等待输入
```

## 外层循环：接收任务并保留上下文

在[模块内的 Python 示例](200lineClaudeCode.py)中，`run_coding_agent_loop()` 先创建 `conversation`，再进入等待用户输入的外层 `while True`。用户输入被追加为一条 `user` 消息，随后控制流进入内层循环。模型完成一次回答后，程序回到输入位置，等待用户继续提出问题。

这里的“新任务”不意味着清空历史。`conversation` 创建在外层循环之前，因此后续输入仍带着前面的消息。这使“继续改刚才的文件”这样的跟进请求具有上下文（Context）。历史保存在内存中；当前脚本退出后不会持久保存对话。

## 内层循环：模型决定下一步，Python 执行工具

内层循环先调用 `execute_llm_call(conversation)`。模型输出的文本交给 `extract_tool_invocations()` 解析：如果得到 `tool: read_file({"filename":"main.py"})` 这样的单行请求，程序就从工具注册表（Tool Registry）取出对应函数并执行。模型生成的是工具名和参数；本地 Python 函数负责实际读取或修改文件。

执行结果被序列化为 `tool_result(...)`，追加到消息历史（Message History），下一轮再连同历史一起发送给模型。因此，同一个任务可以先读文件、再修改文件，最后给出文字说明。工具调用并不结束这个任务；它提供下一步判断需要的信息。

这份示例使用自定义文本协议（Text Protocol）：工具结果以 `user` 消息回传，代码没有传入 API 原生的 `tools` 或 `tool_calls`。描述实现时需要说清这层约定，不能只看到函数名就认为模型已经直接调用了本地函数。

## 用一次文件修改串起整个流程

假设用户输入“查看 `main.py`，把问候语改成 Hello”。外层循环接收这一句，并进入内层循环。第一轮模型可以请求 `read_file`，程序读取文件并回传内容；第二轮模型根据内容请求 `edit_file`，程序完成首次匹配替换并回传结果；第三轮模型返回普通说明，内层循环结束。外层循环随后等待用户的下一条输入。

这是一条用于理解控制流的可能轨迹，不是已经运行过的实验结果。具体模型输出可能不同；示例解析器也可能忽略格式错误的工具请求。

## 结束条件与现有实现的边界

当前代码在没有解析到工具请求时，把回复作为普通回答展示，并跳出内层循环。因此，“没有工具请求”是代码使用的结束条件；它本身不能证明任务已经正确完成。如果模型的工具请求格式错误，也可能走到同一个分支。

工具分支目前只追加执行结果，没有保存模型发出的那条工具请求；后续历史会缺少请求本身。内层循环也没有最大步数或统一的异常处理。这些都是阅读现有实现时需要明确的行为，源码保持原样。外层循环在等待输入时收到 Ctrl+C 或输入结束（EOF）会退出。
