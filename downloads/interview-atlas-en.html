Networking Essentials

Network design determines the path a request follows, the guarantees at each layer, and the behavior under congestion, disconnection, or regional failures. Begin with one complete request, then justify protocols, connection management, and traffic distribution.

The complete path of an HTTPS request

Consider GET /training-jobs/job-42. DNS resolves the destination. If no connection can be reused, the client establishes transport and a TLS session. The HTTP request can then pass through a CDN, load balancer, application, and database before a response returns.

Separate connection setup, network round-trip time (RTT), and service processing time. Fast database work does not remove cross-continent RTT, handshake costs, or proxy queues. Connection reuse avoids repeating setup, so an HTTP request does not necessarily imply a new TCP handshake.

DNS records have caches and TTLs. Changing a record does not instantly migrate every client: failover also depends on cached addresses, existing connections, and reconnect behavior. A successful transport connection says nothing about whether a job or transaction committed.

Responsibilities by layer

LayerResponsibilityWhat it does not guarantee
L3: IPAddressing, routing, and best-effort packet delivery.Arrival or packet ordering.
L4: TCP and UDP; QUIC supplies modern transport capabilitiesEnd-to-end communication with protocol-specific guarantees.Exactly-once business execution.
L7: HTTP, DNS, WebSocket, and othersRequests, responses, or application message formats.Application authorization, recovery, or consistency.

Ports distinguish communication endpoints on a host. Service discovery and load balancing map a logical service onto reachable instances.

TCP, UDP, and QUIC

TCP supplies an ordered, reliable byte stream with retransmission, flow control, and congestion control. It does not preserve application message boundaries: one write can require several reads. Applications need framing through lengths, delimiters, or an upper-layer protocol. Packet loss can delay later bytes while retransmission completes.

UDP sends datagrams without built-in reliable delivery, ordering, or congestion control. It fits workloads that explicitly manage loss and timeliness, such as real-time media. Late audio can be less useful than a dropped fragment. UDP is not automatically faster once an application adds its own reliability and congestion management.

QUIC runs over UDP and adds reliable streams, encryption, and connection management. HTTP/3 uses QUIC; HTTP/1.1 and HTTP/2 commonly use TCP. Independent QUIC streams reduce transport head-of-line blocking across streams, but do not eliminate congestion or all waiting.

HTTP, TLS, and interface semantics

HTTP defines methods, status codes, headers, and bodies. HTTP/1.1 supports persistent connections, while HTTP/2 multiplexes streams. Explain which bottleneck a protocol version addresses rather than treating a version number as a performance result. MDN’s HTTP overview describes clients, servers, and intermediaries.

HTTPS protects confidentiality and integrity in transit and authenticates the server. TLS can terminate at an edge, load balancer, or application. Encrypting the separate backend hop is another deployment decision.

Encryption does not establish resource permission. An owner_id in a request body does not prove ownership. The server still validates identity, ownership, and allowed actions. HTTP’s stateless semantics also do not imply an absence of transport connections or application sessions.

REST, GraphQL, and gRPC

ApproachGood fitCost to explain
RESTPublic resource interfaces, such as creating and reading jobs.Complex pages may need aggregation endpoints or multiple requests.
GraphQLClients needing different fields and related data.Resolver cost, query complexity, N+1 access, caching, and permissions.
gRPCInternal services with explicit contracts or streaming calls.Browser adaptation such as gRPC-Web and compatible infrastructure.

gRPC commonly uses Protocol Buffers and HTTP/2 and can generate multilingual clients. Binary encoding can reduce serialization costs, but end-to-end improvements depend on the workload. REST and GraphQL are interface approaches; TCP and UDP operate at a different layer.

Polling, SSE, and WebSocket

Polling repeatedly requests state. It is straightforward, at the cost of redundant requests and update delay up to a polling interval. It can be sufficient for infrequent updates.

Server-Sent Events (SSE) pushes text events through an HTTP response stream. It fits job progress, notifications, and generated text. Events can carry IDs; EventSource reconnects and can send Last-Event-ID. The application must still retain events, decide retention, and implement replay. Reconnection alone does not guarantee lossless recovery.

SSE deployments must handle proxy buffering, idle timeouts, and heartbeats. HTTP/1.1 browser connection limits may matter. See MDN’s SSE guide for event framing.

WebSocket provides a persistent, bidirectional message channel. A common HTTP/1.1 setup uses Upgrade; other HTTP versions can establish it differently. It fits frequent interaction such as collaborative actions or chat. Applications still define message types, acknowledgments, ordering, heartbeats, and recovery: TCP reliability does not cover business replay after disconnects.

WebRTC and NAT traversal

WebRTC commonly supports browser audio and video. Signaling exchanges session and connection-candidate information; the signaling service need not carry media. ICE gathers and checks candidates, STUN helps discover externally reachable addresses, and TURN relays when direct connectivity fails.

WebRTC therefore does not mean permanent peer-to-peer connectivity without servers. TURN incurs relay bandwidth costs. Multiparty systems often use selective forwarding units (SFUs), avoiding a separate outgoing media stream to every participant. MDN’s connectivity guide explains candidate exchange and connection establishment.

Load balancing requests and connections

Client-side balancing lets a library discover instances and select a target, but requires discovery, health tracking, and client-version management. Dedicated balancers centralize policy and forwarding, while introducing their own capacity and availability concerns.

ChoiceRouting informationImplication
L4IPs, ports, and connection metadata.Usually distributes connections without understanding HTTP paths; implementations may forward or proxy.
L7HTTP hosts, paths, headers, or cookies.Supports content routing, TLS termination, and application policy with protocol-processing cost.

L7 balancers can support WebSocket. Persistent connections do not automatically require L4. Consider Upgrade inspection, routing policy, product support, and capacity. Established connections usually remain attached to their backend, so adding instances may not redistribute existing traffic.

Round robin, least connections, weights, and consistent hashing suit different workloads. Equal connection counts do not imply equal CPU load. Passing health checks does not prove an instance has spare capacity. Sticky sessions can reduce state movement but complicate skew and recovery.

Regions and failures

A CDN reduces distance for reusable content; it cannot remove all coordination from dynamic writes. Regional services require decisions about data ownership, replication, write locations, and failover.

Timeouts bound individual waits; deadlines bound the whole operation. Retries need limits, an overall budget, backoff, and jitter. Retries at several layers amplify load. Side-effecting calls need idempotency. A circuit breaker temporarily rejects calls to a failing dependency and uses limited probes to assess recovery. AWS’s retry design article discusses these engineering choices.

For a training platform, use idempotent HTTPS requests to create jobs, resumable SSE to display progress, and a separate WebSocket channel only where frequent bidirectional interaction requires it.

API Design

An API contract states who may operate on which resources, how inputs are represented, what results and failures mean, and what happens when networks force retries. A training platform provides a concrete example.

Resources and operations

Identify experiments, training jobs, and checkpoints. Put resource identity in paths, optional filters in query parameters, and creation or modification data in request bodies:

POST /training-jobs
GET /training-jobs/job-42
GET /training-jobs?experiment_id=exp-7&state=running&limit=20
POST /training-jobs/job-42/cancellations

Cancellation can be represented as a request resource or an explicit RPC action. More important than naming is whether cancellation completes synchronously, is accepted for later execution, and tolerates repeated submission.

Methods and status codes

MethodTypical semanticsRetry consideration
GETRead a resource safely.Results can change without creating business side effects.
POSTCreate a resource or submit an operation.Application deduplication is needed for idempotency.
PUTReplace or create at a specified address.Repeating the same request should have an idempotent effect.
PATCHModify part of a resource.Setting a value differs from appending an item.
DELETERemove a resource.Final state can be idempotent even when response codes differ.

Return 201 Created for completed creation and 202 Accepted with a status location for accepted asynchronous work. 400 indicates invalid input, 401 missing valid authentication, 403 insufficient permission, 409 a state conflict, and 429 rate limiting. Stable business error identifiers supplement these categories.

Make asynchronous operations observable

Creation can return a job ID, current state, and Location. Later reads expose queued → running → succeeded/failed/cancelled. Accepted cancellation does not prove the GPU worker has stopped.

{
  "id": "job-42",
  "state": "queued",
  "attempt": 1,
  "status_url": "/training-jobs/job-42"
}

State and attempt number should come from controlled records. Failure reasons, retryability, and result locations belong in the contract rather than being inferred from logs.

Bind idempotency to the business commit

Generate an idempotency key for each logical creation and reuse it across network retries. Scope records to the caller, operation, and key, and store a request digest and outcome. Incompatible key reuse should conflict.

Atomicity matters: if creation commits before its deduplication result is saved, a crash can permit duplicate creation. A transaction can store both the idempotency record and job, with a unique constraint handling concurrent requests. Define in-progress responses, retention, and behavior after expiration.

Pagination and query cost

Offset pagination can suit stable small lists and page-number navigation. Large offsets may scan many rows, and concurrent updates can cause skips or duplicates. Cursor pagination instead records an ordering boundary:

WHERE owner_id = :owner
  AND (created_at, id) < (:last_time, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Use a unique ID to break timestamp ties. Bind cursors to filters and order. Cursor pagination alone does not guarantee a cross-page snapshot. Limit page sizes and supported query combinations; design API parameters with indexes.

Identity, permissions, and errors

Authentication establishes identity; authorization grants access to a resource or action. A valid JWT does not prove permission to read job-42. Check ownership or team permissions independently of a supplied owner_id.

Use consistent errors such as {"error":{"code":"JOB_ALREADY_TERMINAL","message":"Job cannot be cancelled"}}. Do not expose internal stacks or credentials. Rate limits may consider users, tenants, and operation costs; retry advice must respect an overall deadline.

GraphQL, gRPC, and evolution

GraphQL suits clients selecting different shapes of overlapping data. Bound query depth and cost, batch related loads, and enforce resource permissions in resolvers. One request can still cause many database queries.

gRPC expresses typed service methods and messages, fitting internal schedulers and workers. Define deadlines, cancellation, streaming, and error mapping. Binary encoding does not remove compute or database bottlenecks.

Optional additions are often easier to evolve than changed meanings, but compatibility depends on clients. Removing fields or changing sort and error semantics can break them. Version numbers do not replace deprecation and migration rules.

Data Modeling

A data model converts access patterns, business invariants, and lifecycle requirements into executable structures. Database selection, indexes, and sharding should follow from those requirements.

Start with reads, writes, and invariants

A training platform lists experiments by owner, finds recent jobs by experiment, reads successful checkpoints, and retries jobs. Its invariants include ownership, protection against stale attempts, and checkpoint publication only after complete writes.

These requirements are more precise than SQL versus NoSQL. Describe queries, sorting, filters, write frequency, and scale. Decide which constraints belong in the database and which require an application protocol.

Entities, keys, and relationships

Experiments have many jobs; jobs have many checkpoints. Membership tables can model users belonging to multiple teams. Use stable system identifiers internally rather than mutable email addresses. Natural identifiers can still have uniqueness constraints.

experiments(id PRIMARY KEY, owner_id, config_version, created_at)
jobs(id PRIMARY KEY, experiment_id, state, active_attempt, version, created_at)
job_attempts(job_id, attempt, worker_id, state, PRIMARY KEY(job_id, attempt))
checkpoints(id PRIMARY KEY, job_id, attempt, step, object_key, state)

Separating logical jobs from execution attempts preserves retry history. Real schemas also need foreign keys, non-null constraints, and appropriate uniqueness rather than relying on every caller to enforce rules.

What different models change

ModelSuitable accessCost
RelationalRelationships, constraints, transactions, and combined queries.Indexes, contention, and distributed scaling still matter.
DocumentNested data commonly read as a bounded aggregate.Unbounded arrays, duplicate updates, and cross-document consistency.
Key-valueExact-key access for sessions, configuration, or caches.Arbitrary filters and joins are usually not its strength.
Wide-columnLarge workloads organized by partition and ordering keys.Queries must be designed ahead of time; hotspots remain possible.
GraphWorkloads dominated by relationship traversal.Additional storage and query complexity; relationships alone do not justify it.

A product category does not establish its exact transaction or consistency guarantees. Specify the operations and guarantees of the actual system.

Normalization and denormalization

Normalization reduces duplication and update anomalies. Denormalization can improve a proven access path, such as storing a latest-job summary with an experiment.

For duplicated views identify the source of truth, update mechanism, and repair process. Asynchronous materialized views reduce read cost but introduce visibility delay and rebuilding. A historical submission-time configuration can be an intentional business fact rather than erroneous duplication.

Protect concurrent state changes

ACID consistency does not guarantee that every concurrent execution matches application intent. Isolation levels, locks, and conditional writes determine observable behavior. PostgreSQL’s isolation documentation distinguishes these guarantees.

UPDATE jobs
SET state = 'running', version = version + 1
WHERE id = :job_id AND state = 'queued' AND version = :expected_version;

Zero updated rows means the record changed, not that acquisition succeeded. Completion should verify attempt numbers or fencing tokens so an expired worker cannot overwrite a newer execution.

Large objects and publication boundaries

Keep weights, archived logs, and datasets in object storage; record locations, sizes, checksums, versions, and publication state in metadata. Object storage and a database generally do not share a local transaction.

One approach writes to a unique temporary location, validates the object, and then commits availability. Garbage collection removes abandoned objects. Readers consume only published records. Versioning, attempt IDs, and idempotent publication help prevent overwrites and duplicate registrations.

Access paths and lifecycle

An index on (experiment_id, created_at, id) supports recent experiment jobs. Owner-wide queries may require another access path. Sharding by experiment preserves locality but can create a hotspot for a huge experiment.

Retention, archives, logical deletion, physical deletion, and audit records affect the schema. Logical deletion does not reclaim storage. Database and object cleanup require retryable workflows and clear retention boundaries.

Database Indexing

An index is an additional maintained access path. It can reduce examined records, accessed pages, and sorting, while consuming storage, cache, and write resources. Begin with a concrete query rather than indexing every field.

Pages, scans, and selectivity

Tables are organized into pages processed in memory. An index narrows candidate records before necessary table access. Cache hits, sequential access, and random access differ, so one logical lookup does not imply one physical disk operation.

When a query returns much of a table, a sequential scan can beat many index-directed table fetches. Optimizers consider selectivity, statistics, distribution, and estimated costs.

B-trees and composite order

B-trees maintain ordered branching structures for equality, ranges, and ordering. Small tree height alone does not determine latency: caching, table fetches, and result count still matter.

CREATE INDEX jobs_by_experiment_recent
ON jobs (experiment_id, created_at DESC, id DESC);

SELECT id, state, created_at
FROM jobs
WHERE experiment_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 20;

This index locates an experiment and follows the requested order. Time-only filtering is a different access path. Choose order from equality, range, ordering, and real distribution, not a universal “most selective first” rule. Some engines support skip-scan optimizations, so left-prefix limitations should not be stated as absolute for every implementation.

Covering, partial, and expression indexes

Covering indexes include returned fields and can reduce table access. PostgreSQL’s INCLUDE (state) adds a payload column, but efficient index-only scans also depend on visibility information.

Partial indexes retain a qualifying subset, such as active jobs, and require compatible query predicates. Expression indexes can support lower(email); a normal index does not automatically accelerate arbitrary expressions. See PostgreSQL’s index documentation.

LSM writes and compaction

LSM engines typically record writes in a WAL and memory structure before flushing sorted files. Compaction merges files and obsolete versions; exact ordering and durability depend on the implementation and configuration.

Batching can replace some random updates, but reads may inspect several files or levels. Bloom filters skip files that cannot contain a key. Compaction consumes background resources. Compare read, write, and space amplification and tail latency rather than calling B-trees read-only or LSM write-only.

Specialized structures

StructurePurposeLimitation
Hash indexExact-key lookup.Does not preserve general ordering for ranges or sorted scans.
Inverted indexMap terms to documents containing them.Tokenization, relevance, visibility, and updates require design.
Spatial indexNarrow candidates by proximity or bounding regions.Usually needs a precise geometric check after filtering.

Geohash encodes spatial cells, but nearby locations can cross boundaries, requiring neighboring cells. Quadtrees recursively divide space; R-tree families organize bounding regions. PostGIS can use GiST-based indexes. Separate ordinary latitude and longitude indexes do not automatically make radius searches efficient.

Write and maintenance costs

Inserts, updates, and deletes can maintain several indexes, adding logs, cache pressure, and storage. Wide frequently changed covering fields can be costly. Unique indexes also enforce constraints and cannot be removed based solely on read usage.

Observe use and maintenance costs instead of prescribing a fixed maximum index count. Online creation must consider locking, extra space, and cleanup after failures.

Verify execution

EXPLAIN displays a plan. EXPLAIN ANALYZE actually executes the statement, so writes and expensive queries are not harmless inspections.

Check scans, estimated versus actual rows, filtered rows, sorts, temporary files, cache hits, and physical reads. Large estimate errors suggest statistics or skew problems. A faster individual query does not prove better overall performance under writes or cold caches.

Caching and Invalidation

Caches retain reusable data or computation results. They trade storage and consistency complexity for lower latency and less backend work. Start with a measured bottleneck and acceptable freshness, rather than adding Redis by habit.

Placement changes the cost

LocationBenefitCost
Client or browserCan eliminate a network call.Versions, capacity, and invalidation are decentralized.
CDN edgeBrings reusable content near users and reduces origin traffic.Cache keys, permissions, regional copies, and invalidation.
Application processAvoids remote-cache latency.Copies diverge across instances and scaling events.
Shared serviceReuses hot data across application instances.Adds network, capacity, and availability dependencies.

Public documents, personalized responses, and private logs cannot blindly share keys. Keys may need tenant, version, parameters, or permission scope in addition to a resource ID.

Read and write responsibilities

Cache-aside makes the application check the cache, load misses, and populate results. Read-through delegates loading to a cache layer or wrapper. These are responsibility boundaries, not interchangeable Redis commands.

Write-through synchronously reaches durable storage before acknowledging completion. Write-back acknowledges cached writes and flushes later, exposing a durability window. Two independent application writes do not automatically form an atomic write-through protocol.

Expiration versus eviction

TTL specifies expiration; eviction selects entries under memory pressure. LRU favors recent use, LFU frequent use, and FIFO insertion order. Implementations can be approximate.

Choose based on hotspot duration, scans, and object sizes. TTL is not automatically a freshness bound measured from a business update: stale readers may populate old values later and restart expiration. See Redis’s eviction reference.

Database updates and invalidation

A common cache-aside pattern commits the database and deletes the cache entry. This does not create a cross-system transaction.

A reader can load old data, another request can update the database and invalidate, and the original reader can then repopulate the stale value. Depending on required guarantees, consider versioned keys, conditional fills, change-driven invalidation, or coordinated reads and writes. Define compensation when invalidation fails and the role of TTL.

Caches should not make unverified final decisions about exact quotas or inventory. Display data tolerating seconds of staleness may need a simpler protocol.

Failure modes

SymptomCauseResponse
StampedeConcurrent rebuilding of a popular result.Single-flight, early refresh, or controlled stale serving.
Repeated nonexistent keysNegative results also receive traffic.Short negative caching; suitable Bloom filters with update handling.
Many expirations togetherSynchronized lifetimes.TTL jitter, staged warmup, and bounded rebuild concurrency.
One overloaded hot keyTraffic skew despite even key counts.Local caching, read replicas, or application splitting with consistency planning.
Cache outageRequests fall through together.Origin limits, concurrency caps, degradation, and circuit breaking.

Direct database fallback is safe only if the database has sufficient headroom.

From hit rate to backend demand

At 12,000 reads/s and a 95% request hit rate, ideal steady-state origin demand is about 600 reads/s. A cache outage can drive it toward 12,000 reads/s. This excludes request merging, multikey requests, and refreshes.

High average hit rates can hide slow misses. Track request and byte hit rates, origin traffic, p95/p99, eviction, memory, and skew. System p99 is not a weighted average of hit and miss p99 values.

Training-platform choices

Immutable terminal-job summaries, versioned configurations, and public model descriptions are good candidates. Active progress needs an explicit refresh policy. Recovery and quota allocation rely on controlled state. Attempt IDs in keys separate retries; generation timestamps help distinguish old data during display and debugging.

Sharding

Sharding distributes a logical dataset across machines to expand capacity or share load. It changes query, transaction, migration, and operational boundaries, not merely the routing formula.

Partitioning, sharding, and replication

Single-instance partitioning creates smaller management units and can help pruning, archiving, and maintenance without adding machines. Sharding usually puts subsets on different machines. Replication copies the same data for resilience or supported read scaling.

They can coexist: shards have replicas and databases can have internal partitions. Read replicas do not automatically remove a primary write hotspot.

Establish a constraint first

Determine whether storage, IO, CPU, logging, locks, or one hot object limits the system. Query and index changes, pooling, batching, larger machines, caching, or read replicas may suffice.

Shard when expected load, growth, recovery time, or geographic requirements justify it. No universal GB or QPS threshold applies. Backup and restore duration can matter even before throughput is exhausted.

Choose a key, then a placement rule

A shard key determines the ownership unit. Good keys spread data and activity while keeping frequent operations local. High cardinality alone does not guarantee balanced traffic.

RuleBenefitCost
RangeNatural range queries and contiguous management.Monotonic writes can overload the newest range.
HashSpreads many distinct keys.Loses range locality and needs an expansion strategy.
DirectoryExplicit placement and large-tenant migration.Requires available, cached, versioned routing metadata.

AWS’s partition-key guidance emphasizes activity distribution, not only record counts.

Change the unit of a hotspot

If one experiment generates half the writes, hashing its ID still selects one destination. Splitting logs by (experiment_id, time_bucket, subshard) creates independently routable write units.

Reads then need multiple shards and merging. Query clients must discover bucket boundaries and subshard counts. Random suffixes without a read plan merely move the bottleneck.

Cross-shard queries and transactions

Fan-out queries aggregate partial results. Global recent-20 queries can merge local candidates, but deep pagination, filters, and unavailable shards complicate semantics. Separate secondary indexes add visibility and consistency questions.

Distributed commit can coordinate transactions, or data ownership can keep critical invariants local. Compensating workflows such as sagas do not equal one atomic transaction. Globally unique IDs do not establish every business uniqueness constraint.

Online expansion is a protocol

One migration approach prepares a target, copies a snapshot, catches up incremental changes, validates, switches routing versions, retains a rollback window, and eventually removes old copies. Define read and write ownership at every stage.

Copy-then-switch can miss concurrent writes. Uncoordinated dual writes can succeed on only one side. Account for duplication, ordering, tombstones, and stale routes, using versions or routing epochs to constrain old owners.

Managed systems still need modeling

A database may automate physical splits and balancing, but it cannot choose the right application access unit. Hot keys, cross-partition transactions, and secondary indexes remain important. Different managed systems do not necessarily use the same hash-ring placement algorithm; rely on their documented mechanisms.

Consistent Hashing

Consistent hashing reduces key reassignment when cluster membership changes. It is a placement and routing method, not a protocol for replica agreement, durability, or recovery.

Why direct modulo complicates expansion

For a fixed cluster, hash(key) % N is simple. Changing N to N+1 remaps many keys. Caches can experience widespread misses; persistent stores need movement and compatibility with old locations.

The issue is coupling ownership directly to physical node count, not modulo itself. Fixed logical partitions mapped separately to machines provide another way to reduce that coupling.

Ring ownership

Place keys and nodes in a circular hash space. A common rule assigns a key to the first clockwise node, wrapping around at the end.

Suppose A=10, B=50, C=90. Key 30 belongs to B, key 70 to C, and key 95 wraps to A. Adding D=35 transfers (10,35] from B to D without changing other intervals. These small integer positions illustrate the rule.

Before: 10(A) ---- 30(key) -------- 50(B) -------- 90(C)
After:  10(A) ---- 30(key) -- 35(D) -- 50(B) ----- 90(C)

With ideal uniform distribution and equal weights, adding a node takes roughly 1/(N+1) of keys on average. This is not an exact guarantee for each expansion, byte volume, or request load.

Virtual nodes

One position per machine can leave a successor overloaded after a failure. Virtual nodes assign several distributed positions to each physical machine, spreading transferred intervals. More positions can represent greater capacity.

Costs include routing metadata and migration management. Virtual nodes cannot split one hot key, and balanced key counts need not imply balanced memory consumption.

Membership and routing versions

Clients, proxies, or servers need a membership view and ring version. Different versions can send the same key to different owners.

Migration can involve forwarding, redirects, or controlled reads from old and new locations. Writes need explicit ownership and cutover rules. Removing a node solely on a local timeout can mistake a partition for failure and create competing writers.

Placement versus recovery

Placement determines where data belongs; replication determines where additional copies exist. Replicas should span physical machines and relevant failure domains. Several virtual nodes on one machine are not independent backups.

Failed caches can rebuild from a source of truth. Durable data needs existing replicas or another recovery source. Expansion still needs historical copying, change catch-up, and validation.

Hotspots and alternative placement

Hot keys may need local caches, replicated reads, splitting, or rate limiting, each with separate consistency and invalidation decisions. Alternatives such as rendezvous hashing also reduce remapping.

Redis Cluster illustrates why product details matter: it maps 16,384 fixed hash slots onto nodes and migrates slots, rather than directly using this virtual-node ring. The Redis Cluster specification documents slots and redirects.

CAP and Consistency Trade-offs

CAP explains incompatible guarantees for distributed data during a network partition. Use it to specify failure behavior for particular reads and writes rather than labeling an entire product CP or AP.

Define the terms

CAP consistency commonly means linearizability: operations appear to take effect between invocation and response while respecting real-time order. A read starting after a successful write cannot return a value superseded by it.

Availability requires requests received by non-failing nodes to eventually obtain corresponding operation results. Indefinite waiting or universal errors do not satisfy it. It is not monthly uptime and does not itself specify a fixed response-time bound.

A partition prevents reliable communication between groups of nodes. Real systems cannot simply choose never to experience one. Without a partition, CAP does not require sacrificing either consistency or availability.

A two-region example

Suppose US and European replicas each show one remaining GPU allocation. During a partition, each receives a request. If both promise success, they can overcommit. If an isolated region waits or rejects because it cannot confirm ownership, those operations lose availability.

Consistency-first does not necessarily stop every service. A majority protocol may continue writes on one side while an isolated minority stops committing. The result depends on the protocol, assumptions, and read path. Drawing a leader alone does not prove strong consistency.

Choose by operation

OperationInvariantPossible partition behavior
Allocate the last GPU quotaNo duplicate resource commitment.Only an authorized owner commits; others wait or fail.
Display progressBrief staleness is acceptable.Return known state with time or version information.
Read a public model descriptionOlder content is acceptable.Serve a local replica and update later.
Publish a checkpointIncomplete objects must not become usable.Control visibility through a publication protocol.

Specify affected records, operations, and invariants. A broad statement such as “the whole system is strongly consistent because it handles money” is insufficient.

Distinguish consistency models

Linearizability concerns real-time order within its specified scope. Serializability makes transaction effects equivalent to some serial execution. Neither automatically implies the other. Strict serializability additionally respects real time.

Read-your-writes and monotonic reads provide session guarantees rather than global linearizability. Eventual consistency converges after writes stop under required communication and repair assumptions; it does not inherently bound convergence time or choose conflict resolution.

ACID consistency concerns valid states and constraints, not CAP’s C. SQL, NoSQL, transactions, and replication are not standalone proofs of cross-region guarantees.

Replication, quorums, and read paths

Synchronous replication coordinates before acknowledgment. Asynchronous replication can return earlier while replicas lag. Leader reads, committed versions, and failover durability affect what clients observe.

R + W > N makes read and write sets overlap, but overlap alone does not prove linearizability. Concurrent writes, version rules, failed operations, membership changes, and recovery still need a correct protocol.

Access paths can differ. DynamoDB’s consistency documentation distinguishes tables and local versus global secondary indexes. A strong option on the base table does not establish identical guarantees elsewhere.

Latency without partitions

PACELC highlights availability versus consistency under partitions and coordination latency versus consistency in normal operation. Cross-continent confirmation introduces network waiting, but implementation details still determine guarantees.

The full client path matters: a strongly consistent database hidden behind an old cache can still expose stale API results. Consider caching, sessions, replication, and failover together.

Capacity Estimation and Orders of Magnitude

Estimates should support decisions: whether one machine suffices, whether caching helps, how long data can be retained, and whether failure leaves enough capacity. Use assumptions and measurements rather than universal vendor benchmark limits.

Convert demand into work

Daily active users are neither simultaneous users nor requests per second. Estimate operations per user and the service calls, database accesses, and messages each operation creates.

Average requests/s = daily operations / 86,400
Peak requests/s = average requests/s × an explicit peak factor
Backend reads/s ≈ requests/s × reads/request × miss rate

Peak factors depend on time zones, scheduled work, events, and tenant skew. Fan-out, retries, and background work increase internal traffic beyond external demand.

A complete log-ingestion example

Assume 10 million daily records, 2 KB each in decimal units, and a 10× peak. These are illustrative assumptions, not measurements.

ItemCalculationResult
Average ingestion10,000,000 / 86,400About 116 records/s.
Peak ingestion116 × 10About 1,160 records/s.
Daily raw data10,000,000 × 2,000 B20 GB/day.
Thirty-day raw retention20 × 30600 GB.
Three raw replicas600 × 31.8 TB.
Peak payload bandwidth1,160 × 2,000 B/s × 8About 18.6 Mb/s.

Indexes, metadata, headers, replication traffic, backups, and compression remain separate. Three replicas are not three independent historical backups: deletion can propagate to all copies.

Latency, throughput, and concurrency

Latency measures request duration; throughput measures completed work per time; concurrency measures simultaneous work. They are not interchangeable.

In a stable system, Little’s Law uses averages: average in-flight work equals average arrival rate times average time in the system. At 2,000 requests/s and 0.1 s average duration, expect about 200 in-flight requests. Do not substitute p99 or treat an indefinitely growing queue as steady state.

End-to-end p99 is not simply the sum of component p99 values. Fan-out, correlated failures, and queuing affect tails. Allocate budgets and verify the complete path.

Calculate resource dimensions separately

CPU depends on computation and parallel efficiency. Memory includes resident data, connection buffers, and object overhead. Storage needs capacity, IOPS, bandwidth, and durability analysis. Network traffic includes responses, replication, and cross-region exchange.

At an assumed 32 KiB per active connection, 100,000 connections use about 3.05 GiB for that component alone. This is not a fixed server overhead; TLS, application, and kernel state may add costs. Bandwidth capacity also does not determine small-request throughput when CPU or packet processing dominates.

Avoid fixed QPS limits

Point reads, joins, large transactions, durable writes, and large responses impose different costs on identical hardware. Indexes, cache state, connections, batching, and contention change results.

Report dataset size, distribution, read/write mix, payload, durability, cache state, latency targets, and errors. Sustainable capacity means throughput meeting those targets, not the highest brief rate before collapse.

Failure and recovery headroom

A cluster sufficient in normal operation may fail after losing a node or zone. Calculate remaining capacity and reserve room for replication, warmup, backlog recovery, and deployments.

Queues postpone work rather than creating capacity. At 1,500 arrivals/s and 1,200 completions/s, backlog grows by 300/s. Recovery needs processing above new arrivals. Under stable assumptions, drain time is approximately backlog / (processing rate - arrival rate).

Turn estimates into decisions

Find the tightest resource and compare targeted changes: fewer queries, better indexes, batching, or larger machines. Introduce caching, asynchronous work, or sharding when measurements and growth justify them.

Compare scenarios such as doubled record size or a peak factor rising from 10 to 20. Identify which uncertainty changes the design. Real cloud cost comparisons require current region- and configuration-specific prices.

The Two Loops of a Coding Agent

The diagram preserves the central idea of the original note: the outer loop accepts a new user task, while the inner loop advances the current task. This distinction connects three responsibilities: model generation, tool execution, and conversation history.

The core of a coding agent:
Outer loop: wait for a user task
    ↓
Inner loop: request model → execute tool → return result to model
    ↑                                           ↓
    └────────── model needs another tool ────────┘
                                                ↓
                                      model answers directly
                                                ↓
                                      return to user input

Outer loop: accept a task and retain context

In the Python example in this module, run_coding_agent_loop() creates conversation before entering the outer while True loop that waits for user input. The input is appended as a user message, and control moves into the inner loop. Once the model finishes an answer, the program returns to the input prompt and waits for another question.

A new task does not clear the history here. Because conversation is created before the outer loop, later inputs retain earlier messages. This provides context for follow-ups such as “continue editing that file.” History lives in memory; the current script does not persist the conversation after exit.

Inner loop: the model chooses the next step and Python executes tools

The inner loop first calls execute_llm_call(conversation). The model’s text is parsed by extract_tool_invocations(). If it yields a single-line request such as tool: read_file({"filename":"main.py"}), the program selects the corresponding function from the tool registry and executes it. The model generates a tool name and arguments; a local Python function performs the actual file read or edit.

The result is serialized as tool_result(...) and appended to the message history. The next iteration sends it back to the model along with the history. A single task can therefore read a file, edit it, and finally produce an explanation. A tool call does not end the task; it supplies information needed for the next decision.

This example uses a custom text protocol: results are returned as user messages, and the code does not pass the API’s native tools or tool_calls. Explain this convention when describing the implementation. A function name appearing in model output does not itself execute a local function.

Follow one file edit through both loops

Suppose the user enters “Inspect main.py and change the greeting to Hello.” The outer loop accepts the input and enters the inner loop. The first model response might request read_file, after which the program reads and returns the content. The second response might request edit_file based on that content; the program replaces the first matching occurrence and returns the result. A third response gives an ordinary explanation, ending the inner loop. The outer loop then waits for another user input.

This is a possible trace for explaining control flow, not the result of an experiment that was actually run. The model may produce different output, and the example’s parser may ignore malformed tool requests.

Termination and the boundaries of the current implementation

When no tool request is parsed, the current code displays the response as an ordinary answer and exits the inner loop. “No tool request” is therefore the implemented termination condition; it does not itself prove that the task was completed correctly. A malformed tool request can reach the same branch.

The tool branch currently appends only the execution result and omits the model’s tool request, leaving that request absent from later history. The inner loop also has no maximum step count or shared exception handling. These are behaviors to identify when reading the existing implementation; the source code remains unchanged. The outer loop exits when Ctrl+C or end-of-input (EOF) occurs while waiting for input.
