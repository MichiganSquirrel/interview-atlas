Networking Essentials

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

DNS resolves names; TCP offers an ordered, reliable byte stream; TLS protects the connection; HTTP defines requests and responses. HTTP/3 uses QUIC over UDP, so HTTP does not always imply TCP.

Load balancing distributes traffic across instances. L4 uses connection metadata, while L7 can route by HTTP paths and headers. Persistent connections require connection limits, keepalives, and reconnect behavior.

Practice: training-job progress

Submit jobs over HTTP. Consider Server-Sent Events (SSE) for one-way progress updates and WebSocket for bidirectional interaction. Establish latency and connection targets before selecting a protocol.

Follow-upReasoning
Does a successful connection prove success?TCP delivery does not prove a committed transaction; use application acknowledgments and idempotency.
Why set timeouts?Bound waiting and combine limited retries with backoff and jitter.
Are network calls always slow?Check distance, serialization, connection reuse, and tail latency.

Self-check

  • Trace a browser request and explain the user-visible effect of each failure.
  • Explain L4 forwarding versus L7 routing.

API Design

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

Identify resources and access patterns before selecting a protocol. REST fits ordinary resource operations, GraphQL lets clients select fields, and gRPC suits service calls with explicit contracts.

Idempotency means repeated execution leaves the same business state; response codes need not match. PUT and DELETE have idempotent semantics. POST can implement business idempotency with a key; PATCH depends on the operation.

Practice: submit a training job

POST /training-jobs
Idempotency-Key: client-generated-key

{"dataset_id":"ds-42","config_version":"v3"}

Return 202 Accepted, a job identifier, and a status location. Use GET /training-jobs/{id} for progress. Bind each idempotency key to the caller and request digest to detect incompatible reuse. Authorize using server-verified identity, rather than a client-provided user ID.

Use cursor pagination for lists. Include a unique identifier in the ordering to break timestamp ties.

Self-check

  • A request commits but the client times out. How does retry avoid creating a second job?
  • Explain when to return 400, 401, 403, 404, 409, and 429.
  • How can concurrent inserts cause skips or duplicates with offset pagination?

Data Modeling

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

Work backward from queries and invariants to entities, primary keys, relationships, and constraints. A relational database is a common starting point. Justify document, key-value, or graph models with specific access patterns.

Normalization reduces duplication and update anomalies. Denormalization improves reads through duplication but adds update and repair costs. ACID transactions do not remove the need to choose an isolation level.

Practice: experiments, jobs, and checkpoints

experiments(id PRIMARY KEY, owner_id, config_version)
jobs(id PRIMARY KEY, experiment_id, state, attempt)
checkpoints(id PRIMARY KEY, job_id, object_key, step)

Keep model weights in object storage; store locations, versions, and checksums in tables. Attempt numbers distinguish retries. Use conditional state transitions so an old worker cannot overwrite a newer attempt. A checkpoint becomes usable only after its payload is complete and its metadata is committed.

Self-check

  • How would you query an experiment’s latest successful checkpoint, and which index supports it?
  • How would you remove orphaned objects after deleting a job?
  • What growth and concurrency problems arise when all history is embedded in one document?

Database Indexing

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

Indexes reduce the pages read to locate records. B-trees support equality, ranges, and ordering; hash indexes focus on equality; inverted indexes support term search; spatial indexes support location queries. LSM structures trade write, merge, and read costs.

Indexes consume storage and add write maintenance. Composite column order should match filters and ordering. Whether a covering index avoids table access also depends on database-specific visibility conditions.

Practice: recent jobs for an experiment

CREATE INDEX jobs_experiment_recent
ON jobs (experiment_id, created_at DESC, id DESC);

SELECT id, state, created_at FROM jobs
WHERE experiment_id = 42
ORDER BY created_at DESC, id DESC LIMIT 20;

The index locates one experiment and scans in time order. A query filtering only by state may behave differently. Verify scanned rows, sorts, and actual runtime with EXPLAIN. Low-selectivity queries may favor a sequential scan.

Self-check

  • Why avoid indexing every column?
  • Why is (a,b) different from (b,a)?
  • Explain trade-offs among write throughput, read latency, and space amplification.

Caching & Invalidation

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

Caching exchanges storage and consistency complexity for better read latency and lower backend load. Caches can live in clients, CDNs, application processes, or shared services. Cache-aside reads the cache first, loads misses from the database, and fills the cache.

TTL limits residence time but does not independently guarantee an acceptable freshness bound. Eviction differs from expiration. Write-through, write-back, and invalidation strategies have different durability risks.

Practice: reading training-job status

Terminal job states change rarely and are good cache candidates. Refresh active states according to freshness requirements. Include attempt or version identifiers in keys to avoid stale workers repopulating old values.

FailureResponse
Hot entries expire togetherSingle-flight fetching and expiration jitter.
Repeated nonexistent keysShort-lived negative caching; consider a Bloom filter when appropriate.
Cache outageRate limits, degradation, and bounded origin concurrency to protect the database.

Self-check

  • What if a database update succeeds but invalidation fails?
  • Can a stale reader overwrite a newly cached value?
  • Why can p99 remain poor despite a high hit rate?

Sharding

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

Sharding distributes data across machines. Partitioning often divides tables inside one database instance. Replication keeps copies and does not by itself distribute primary writes.

Measure whether indexing, query optimization, vertical scaling, or read replicas can solve the bottleneck first. A shard key must balance traffic distribution, locality, and hotspots. Hash, range, and directory routing have different maintenance costs.

Practice: training logs

Sharding by experiment_id keeps experiment queries local, but a huge experiment can create a hot shard. Time buckets or subshards spread writes while increasing read fan-out. Global search may need a separate search index.

Explain expansion through historical migration, incremental replication or dual writes, routing cutover, validation, and rollback. Include cross-shard transactions and global ordering in the cost.

Self-check

  • If one user generates half of all writes, does hashing the user ID help?
  • How do you merge the latest 20 records from several shards?
  • How do routing-version mismatches cause missed reads or duplicate writes?

Consistent Hashing

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

With hash(key) % N, changing the node count remaps many keys. Consistent hashing maps keys and nodes onto a hash ring; a common implementation assigns each key to its clockwise successor.

Virtual nodes give each machine multiple ring positions, improving distribution and representing capacity weights. Under ideal uniform distribution, adding one node to N nodes moves roughly 1/(N+1) of keys; this is not an unconditional workload guarantee.

Practice: model-metadata cache

A new node takes responsibility for its new ring intervals. A cache can rebuild entries under the new routing. Durable databases also need data migration, routing versions, reads and writes during migration, and replica recovery.

Consistent hashing does not guarantee replica consistency or solve a single hot key. Address hotspots through splitting, replicated reads, or application rate limits.

Self-check

  • Draw a three-node ring, add a fourth node, and mark moved intervals.
  • How do virtual nodes affect routing metadata and operations?
  • How does failure recovery differ from planned expansion?

CAP & Consistency Trade-offs

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

CAP concerns the trade-off between consistency and availability during a network partition. Its consistency means linearizability, not ACID consistency. Its availability requires requests received by non-failing nodes to eventually receive responses; it is not an uptime percentage.

CAP does not mean freely choosing any two properties at all times. During a partition, some operations may be rejected or delayed to preserve consistency. Continuing to serve can sacrifice a single real-time global view. PACELC also highlights latency versus consistency when the network is healthy.

Practice: GPU quotas and progress views

Quota allocation needs explicit concurrency invariants. Reject allocations during a partition if necessary to avoid duplicate commitments. Progress displays can often tolerate stale data and converge later. Choose semantics per operation rather than labeling an entire product CP or AP.

Eventual consistency promises convergence under its assumptions; it does not automatically bound staleness or specify conflict resolution.

Self-check

  • Explain reads and writes when two regions lose connectivity.
  • Why does using SQL not prove cross-region linearizability?
  • Distinguish read-your-writes from linearizability.

Capacity Estimation & Orders of Magnitude

Scope: concise notes based on the publicly accessible article and topic outline. Practice scenarios and self-checks are original; Premium videos, quizzes, and restricted text are not reproduced.

Core decisions

Capacity estimates support decisions; single-machine benchmark results are not universal limits. Throughput depends on hardware, workload, object size, indexes, batching, and durability requirements. A fixed database QPS claim lacks necessary context.

Distinguish averages, peaks, and tail latency. State assumptions, units, and headroom before choosing caching, sharding, or asynchronous processing. Revise estimates with measurements.

Practice: log ingestion

Assume 10 million records per day, each 2 KB in decimal units. Average ingestion is 10,000,000 / 86,400 ≈ 116 records/s. A 10× peak is about 1,160 records/s. Raw storage is about 20 GB/day, or 600 GB for 30 days. Three replicas require about 1.8 TB before indexes and compression.

Little’s Law: in a stable system, average in-flight work equals arrival rate times average time in the system. At 2,000 requests/s and 0.1 s average duration, expect about 200 in-flight requests. Do not substitute p99 for the average.

Self-check

  • Why must bytes and bits be kept distinct?
  • Can remaining capacity handle the peak after losing a zone?
  • Which assumption is most likely to change the architecture decision?

Practical Delivery & Acceptance Checklist

A complete practice loop
