网络基础

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

域名系统（DNS）负责查址；TCP 提供有序、可靠的字节流；TLS 保护连接；HTTP 定义请求与响应。HTTP/3 基于 QUIC/UDP，不应把所有 HTTP 都说成 TCP。

负载均衡（Load Balancing）把流量分散到实例。四层（L4）依据连接信息，七层（L7）可依据 HTTP 路径或头部。长连接需要考虑连接数、保活与重连。

面试推演：训练任务进度

提交训练任务走 HTTP 请求；服务端单向推送进度可用服务器发送事件（SSE）；双向交互再考虑 WebSocket。先定义延迟和连接规模，再选协议。

追问回答抓手
连接成功代表业务成功吗？TCP 成功不代表事务已提交，应用层要有确认和幂等。
为什么要超时？限制等待时间，配合有限重试、退避（Backoff）和抖动（Jitter）。
网络调用真的很慢吗？看跨区域距离、序列化、连接复用和尾延迟（Tail Latency）。

自测

  • 画出浏览器到服务的路径，并说明每一层失败时用户看到什么。
  • 解释 L7 路由与 L4 转发的差别。

API 设计

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

先确认资源（Resource）和访问方式，再选协议。REST 适合常见资源操作；GraphQL 适合客户端按需选择字段；gRPC 适合有明确契约的服务间调用。

幂等性（Idempotency）指重复执行后的业务状态一致，不要求每次返回相同状态码。PUT 和 DELETE 具备幂等语义；POST 可以通过幂等键获得业务幂等；PATCH 取决于操作内容。

面试推演：提交训练任务

POST /training-jobs
Idempotency-Key: client-generated-key

{"dataset_id":"ds-42","config_version":"v3"}

返回 202 Accepted、任务标识与状态查询位置；GET /training-jobs/{id} 查询进度。幂等键必须绑定调用者和请求摘要，避免同键不同请求。鉴权（Authorization）依据服务端身份，不能信任请求体里的用户编号。

列表用游标分页（Cursor Pagination）；排序字段加唯一标识，避免时间相同导致翻页不稳定。

自测

  • 请求已提交但客户端超时，重试如何避免创建两个任务？
  • 说明 400、401、403、404、409、429 的适用情况。
  • 分页期间新增数据时，偏移分页（Offset Pagination）可能怎样漏读或重读？

数据建模

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

从查询与不变量（Invariant）反推实体、主键（Primary Key）、关系和约束。关系型数据库（Relational Database）是常见起点；选文档、键值或图模型时，需要说明具体访问模式。

规范化（Normalization）减少重复与更新异常；反规范化（Denormalization）用重复数据换取读取效率，同时引入更新与修复成本。事务的 ACID 不能替代对隔离级别（Isolation Level）的说明。

面试推演：实验、任务与检查点

experiments(id PRIMARY KEY, owner_id, config_version)
jobs(id PRIMARY KEY, experiment_id, state, attempt)
checkpoints(id PRIMARY KEY, job_id, object_key, step)

模型权重放对象存储（Object Storage），表里保存位置、版本与校验信息。任务尝试编号区分重试；状态转换采用条件更新，防止旧工作进程覆盖新尝试。检查点是否可用，以完整写入和元数据提交为界。

自测

  • 如何查询某个实验最新的成功检查点？该建什么索引？
  • 删除任务后，如何清理对象存储中的孤立文件？
  • 把所有运行历史嵌进单个文档，会遇到哪些增长和并发问题？

数据库索引

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

索引（Index）减少定位记录时读取的数据页。B-tree 适合等值、范围和排序；哈希索引（Hash Index）侧重等值；倒排索引（Inverted Index）适合词项检索；空间索引（Spatial Index）支持位置查询。LSM 结构以写入、合并与读取成本作权衡。

索引会消耗空间并增加写入维护开销。复合索引（Composite Index）的列序要匹配过滤与排序；覆盖索引（Covering Index）是否避免访问表数据还取决于数据库的可见性等条件。

面试推演：读取某实验最近的任务

CREATE INDEX jobs_experiment_recent
ON jobs (experiment_id, created_at DESC, id DESC);

SELECT id, state, created_at FROM jobs
WHERE experiment_id = 42
ORDER BY created_at DESC, id DESC LIMIT 20;

这个索引优先定位实验，再沿时间顺序读取。改成仅按 state 查询，效果可能不同。用执行计划（EXPLAIN）验证扫描行数、排序和实际耗时；低选择性（Selectivity）查询未必适合索引。

自测

  • 为什么不能给每一列都加索引？
  • (a,b) 为什么不等同于 (b,a)？
  • 写入吞吐、读取延迟、空间放大之间怎么取舍？

缓存策略与失效

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

缓存（Cache）用空间和一致性复杂度换取读延迟与后端负载改善。可放在客户端、CDN、应用进程或共享缓存层。旁路缓存（Cache-aside）先读缓存，未命中再读数据库并回填。

生存时间（TTL）限制驻留时间，但不自动保证业务允许的最大陈旧度。淘汰（Eviction）与过期（Expiration）不同。写穿（Write-through）、写回（Write-back）和失效策略具有不同持久性风险。

面试推演：任务状态读取

训练任务终态很少变化，适合缓存；活跃状态应依据进度新鲜度要求设置刷新策略。键加入尝试编号或版本，避免旧工作进程回填过期值。

故障处理方向
热点同时过期（Stampede）单次回源（Single-flight）、过期时间抖动。
不存在的键持续穿透短时负缓存（Negative Caching），必要时加布隆过滤器。
缓存整体不可用限流、降级与回源并发上限，保护数据库。

自测

  • 数据库更新成功，但缓存删除失败怎么办？
  • 读到旧值后回填，能否覆盖刚写入的新值？
  • 命中率很高时，为什么 p99 仍可能很差？

数据分片

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

分片（Sharding）把数据分散到多台机器；单实例分区（Partitioning）通常仍在同一个数据库实例内。复制（Replication）保存副本，不能直接替代写入分片。

先用测量判断瓶颈能否由索引、查询优化、纵向扩容或读副本解决。分片键（Shard Key）必须兼顾流量分布、数据局部性与热点；哈希、范围、目录路由各有维护成本。

面试推演：训练日志

以 experiment_id 分片可聚合实验查询，但超大实验会成为热分片（Hot Shard）。加入时间桶或子分片可以分散写入，同时增加读取扇出（Fan-out）。全局搜索可能需要单独的检索索引。

扩容要说明：存量迁移、增量复制或双写、路由切换、校验与回滚。跨分片事务（Cross-shard Transaction）和全局排序的成本也必须计入。

自测

  • 单个用户占一半写流量时，哈希用户编号能解决吗？
  • 跨分片取最近 20 条记录怎么合并？
  • 路由版本不一致时，如何避免漏读和重复写？

一致性哈希

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

直接使用 hash(key) % N，节点数量变化会重映射大量键。一致性哈希（Consistent Hashing）把键与节点映射到同一哈希环（Hash Ring），常见实现选择顺时针的后继节点。

虚拟节点（Virtual Node）让单机占据多个环位置，改善分布并表达容量权重。理想均匀分布下，从 N 个节点增加一个节点大约迁移 1/(N+1) 的键；这不是任意工作负载下的严格保证。

面试推演：模型元数据缓存

节点加入后，只迁移它新接管的区间。缓存可以按新路由重建；持久化数据库还要处理数据搬迁、请求路由版本、迁移期间读写与副本恢复。

一致性哈希不保证副本数据一致，也不会自动解决单个超热键。热点需要拆分、复制读取或业务级限流。

自测

  • 在纸上画三个节点的环，再加入第四个节点，标出迁移区间。
  • 虚拟节点增加后，路由元数据和运维成本怎样变化？
  • 节点宕机与主动扩容的处理有哪些不同？

CAP 与一致性取舍

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

CAP 讨论网络分区（Network Partition）发生时，一致性（Consistency）与可用性（Availability）的取舍。这里的一致性指线性一致性（Linearizability），不是 ACID 的一致性；可用性指非故障节点收到的请求最终得到响应，并非业务可用率指标。

不能把 CAP 理解为任何时候任意选两个。分区时，一侧可能拒绝或等待请求以维护一致性；继续服务则可能失去单一的全局实时视图。PACELC 还提醒我们，正常网络下也存在延迟与一致性的权衡。

面试推演：GPU 配额与进度展示

GPU 配额扣减需要明确的并发不变量，分区时可以选择拒绝分配，避免重复承诺。训练进度展示通常可以容忍短暂陈旧，允许稍后收敛。按操作选择语义，不能给整个产品只贴一个 CP/AP 标签。

最终一致性（Eventual Consistency）承诺在满足条件时收敛，但不自动承诺最大陈旧时间或冲突处理方式。

自测

  • 用两个区域断连的例子，说明读和写分别如何处理。
  • 为什么“用了 SQL”不能证明跨地域线性一致？
  • 如何区分读己之写（Read-your-writes）与线性一致性？

容量估算与数量级

范围：基于公开可访问的原文和主题目录整理；以下面试推演与自测为原创练习，不复刻 Premium 视频、测验或受限正文。

核心判断

容量估算（Capacity Estimation）用来支持决策，不能把单机性能背成通用上限。吞吐取决于硬件、负载、对象大小、索引、批处理和持久性要求；“某数据库固定支持多少 QPS”缺少必要前提。

先区分平均值、峰值和尾延迟。写出假设、单位与余量（Headroom），再判断是否需要缓存、分片或异步处理。数字必须能由实测校正。

面试推演：日志写入

假设每天 1,000 万条、每条 2 KB（十进制），平均写入约 10,000,000 / 86,400 ≈ 116 条/秒；峰值取 10 倍约 1,160 条/秒；原始数据约 20 GB/天。保留 30 天约 600 GB，三副本约 1.8 TB，尚未包含索引和压缩。

利特尔定律（Little’s Law）：稳定系统中，平均在途请求数约为到达率乘平均停留时间。2,000 请求/秒、平均 0.1 秒，对应约 200 个在途请求；不能代入 p99 作为平均值。

自测

  • 为什么字节（Byte）和比特（bit）不能混算？
  • 单区故障后，剩余容量能否承担峰值？
  • 哪个假设变化最可能改变架构结论？

实战交付与验收清单

一次练习的完整闭环

需求澄清 → 最小实现 → 工具验证 → 人工评审 → 复盘。先定义验收条件（Acceptance Criteria），再让 AI 拆解任务。

  • 上下文（Context）：输入、输出、已有接口、运行环境、不可改变的约束。
  • 工具（Tools）：文件搜索、运行测试、检查日志与查看差异。
  • 调试（Debugging）：复现 → 缩小范围 → 提出假设 → 验证 → 修复。
  • 评审（Review）：正确性、失败路径、依赖、凭据处理与可维护性。
  • 证据（Evidence）：实际运行结果、尚未覆盖的边界和下一步。

强化学习系统知识地图

本页是待填充的复习框架，不代表已有项目经历或已掌握程度。

维度需要回答的问题
目标与算法（Objective / Algorithm）优化什么目标？优势估计、裁剪、KL 约束如何影响训练？
数据流（Data Flow）提示词 → 采样（Rollout）→ 奖励（Reward）→ 训练批次如何流转？
系统执行（Execution）训练与推理资源如何分配？同步和异步各有什么代价？
性能（Performance）吞吐、GPU 利用率、长尾、显存、通信分别怎么测？
稳定性（Stability）旧策略数据、版本错配、数值异常、奖励投机怎样发现？
恢复（Recovery）检查点、重试、去重与可复现性需要保存什么？
评估（Evaluation）怎样区分奖励提升、泛化改善和评估污染？

技术证据

维度需要补充的材料
范围（Scope）我做了什么、团队做了什么、哪些没有做。
架构（Architecture）数据流、接口、存储、依赖和部署边界。
决策（Trade-off）候选方案、约束、选择依据和放弃原因。
结果（Outcome）基线、测量方法、样本规模、误差与实际指标。
故障（Failure）复现条件、根因、修复、如何避免复发。
深挖（Follow-up）规模十倍、节点故障、数据陈旧时怎样调整。
